# Conversations and staff notes

`features.conversations` gates every channel. Organization and division channels are staff-authored announcements. Team channels, and published event channels, are youth group channels for the current roster household, coaches, and staff. Direct messages are rejected.

Guardians and linked participants can read a youth channel before the organization approves youth posting. A guardian sees only messages created at or after the earliest currently active eligible guardian grant's `grantedAt`; revocation followed by a new approval starts a new history window. That cutoff also applies to search, pinned-message projection, edits, reactions, cursors, and linked attachment downloads. A self-linked participant, staff member, or coach keeps the existing full-history behavior. Guardians can post only when `policies.youthChannels` is `approved`. Staff and coaches can post and pin before that approval. A channel keeps at most three pins. Program staff and org admins can tombstone a message, which removes its text from later reads.

Staff notes are stored at `organizations/{orgId}/staffNotes/{scopeType}_{scopeId}/entries/{noteId}`. They are not messages, notifications, or outbox rows. Coaches and households cannot read them.

Clients cannot read or write conversation or staff-note documents. Account deletion replaces raw actor identifiers in retained organization records with `Deleted user`, removes reactions, and deletes unfinished or unlinked attachment data.

A guardian grant counts only when its document path is the participant's guardian record in that organization and the participant is still active. Organization announcement reads scan the caller's bounded guardian grants and keep a schedule grant even when another profile-only grant is also active. Message and staff-note lists return a cursor; the native screen and admin page can load the next page.

Message pages are newest first, ordered by the server sequence. The cursor is `s{sequence}_{messageId}` and is accepted only when that message still belongs to the channel at that sequence. Page size stays 1 through 50, and clients ask for 25.

The author of a message can replace its text with `editConversationMessage`. The command requires the current message revision and a new request id. A moderator still tombstones through `moderateConversationMessage`; a tombstone keeps the sequence and removes the text. Both actions append an edit record with the actor, revision, and time. That record does not store the previous text. Search tokens are replaced on edit and deleted on tombstone.

Reactions are the seven allowlisted emoji in `CONVERSATION_REACTIONS`. `reactToConversationMessage` toggles one reaction for the caller. The same posting permission applies, so a guardian cannot react while youth posting is closed. The expected revision is the message text revision. A reaction does not change that revision.

`searchConversationMessages` matches exact normalized words inside one authorized channel. Tokens are at least two letters or numbers, queries contain one to five words, and a message can index at most 200 unique words. Before reading the index, a request backfills at most 100 messages that were stored before the index existed, records how far that walk has gone, and sets `partial` while older messages remain. The backfill re-reads each message inside a transaction before writing its index, so a concurrent edit is not replaced with stale tokens. While that walk is unfinished, the continuation cursor restarts the index scan instead of advancing past the partial index, and clients drop duplicate hits. The server then reads the private `messageSearch` index in batches of 200, checks the current message revision and text, and returns at most 50 hits. A request stops after 1,000 candidates. A continuation cursor is returned only when another candidate or an unfinished backfill remains, including when a page or the cap ends on an exact boundary. The cursor is HMAC-signed with Secret Manager `CONVERSATION_SEARCH_CURSOR_KEY`, a JSON key ring `{"active":2,"keys":{"1":"<previous>","2":"<current>"}}` whose values are at least 32 characters. The active id signs new cursors and older ids still verify until they are removed. The demo emulator uses a public synthetic ring only. Staff notes are not indexed and do not appear in results. A revoked reader gets no results.

Native navigation opens the same household channel. A household calendar with a participant on the team offers that organization's announcements, the division announcements, the team channel, and each loaded event channel. A coach-only calendar team offers the team channel. The team tab offers the team channel when the live team read includes its organization. Event detail offers the published event channel. Offline copies hide these actions. A denied read shows an unavailable conversation and does not reveal staff notes.

A channel page also reports `attachments` as `enabled` or `disabled`, and `canPost`. Those fields hide the picker. A household message may include up to 3 ready attachment ids from the author. The page returns each linked file's name, detected type, and stripped byte length, and a tombstone hides them. Staff notes cannot carry files. The contract is in `docs/attachment-transport.md`. `features.attachments` stays off unless an organization turns it on.

## Reports, blocks, and moderation (App Store 1.2)

`reportConversationMessage` lets any reader of a channel report another person's visible, not yet removed message with a reason (`harassment`, `inappropriate`, `safety`, `spam`, `other`) and an optional note of up to 500 characters. The report id is derived from the reporter and message, so repeating a report returns the existing one with `duplicate: true`, and the request id makes retries idempotent. A report never hides or deletes the message. It stores the reporter, author, reason, note, and a copy of the text at report time so a later edit cannot erase the evidence. Reports live at `organizations/{orgId}/conversationReports/{reportId}` and are callable-only.

`listConversationReports` is the moderation queue. Org admins see every open report in the organization. Program staff see open reports for their programs and for organization announcements. Coaches, households, and other organizations are denied. Only this queue returns the reporter's identity. `resolveConversationReport` rechecks the caller's live staff grant against the report's program, the same scoping as the queue, so a report stays resolvable after its team or division is archived. `dismissed` closes the report and keeps the message. `removed` writes the same tombstone as `moderateConversationMessage` when the message is not already removed, and closes the other open reports on that message 200 at a time; `remaining: true` means the caller should repeat the command, and a repeat on an already removed report continues that cleanup. Resolution deletes the stored text copy. The native Safety screen repeats until nothing remains, behind a destructive confirmation. Messages whose author deleted their account can still be reported but not blocked.

`blockConversationMember` blocks the author of a message the caller can read. Blocks are per organization and stored at `organizations/{orgId}/userBlocks/{blockId}`, at most 100 per person. The semantics are:

- Blocking is available only to household readers (guardians and linked participants) of team and event channels. Staff and coaches supervise those channels and moderate instead, so they cannot block and their views are never filtered.
- Current org staff and coaches of the channel's teams cannot be blocked, and a block on someone who later becomes staff or coach stops hiding them. Organization and division announcements are never filtered, so a guardian always sees staff communication.
- `listConversationMessages` and `searchConversationMessages` drop the blocked author's messages, pins, and attachments on the server for the blocker only. Message pagination advances past hidden messages, so a page can hold fewer items than requested.
- Blocking does not notify the blocked person, change what anyone else sees, or hide reports. A blocked person's messages can still be reported and moderators still see them.
- `listConversationBlocks` returns the caller's blocks with where each started, not the blocked identity. `unblockConversationMember` deletes the caller's own block and stays available after access is revoked, because it only widens what the caller sees.

Follow-up: account deletion does not yet scrub reporter and blocker identifiers in these two collections.
