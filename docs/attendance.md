# Manual attendance and completion rosters

P2.10 records actual attendance independently of intended RSVP. An assigned coach or live scoped organization staff member can record Unknown, Present, Late, Absent or Excused for a participant on their team. Participant IDs are canonical organization identities, never login UIDs. No participant device, check-in or RSVP is required. Missing attendance and attendance from an earlier schedule version both read as Unknown. Completion never creates absence records.

## Commands and privacy

`getEventAttendance({eventId, teamId, pageSize?, cursor?})` returns one authorized team roster page (1–50, default 50), intended RSVP labels, actual attendance revisions and source, and completion snapshot metadata. `recordEventAttendance({eventId, teamId, participantId, expectedRevision, eventRevision, scheduleVersion, status, reason?, requestId})` checks the participant revision, event revision and schedule version atomically. Every subsequent record and every post-completion record requires a reason, including corrections back to Unknown. The server sets source `coach`, actor, timestamps and correlation ID. Current state is at `events/{eventId}/attendance/{participantId}` and immutable revisions are under its `history` subcollection.

`getAttendanceHistory({eventId, teamId, participantId, pageSize?, cursor?})` returns revision-ordered, paged audit entries. Audit cursors are positive revision numbers; roster cursors are participant document IDs. Every page checks current canonical staff or assigned coach authority. Captains without a coach/staff grant, platform support roles, household grants and discovery pointers confer no attendance access. A coach cannot read the opponent's roster, response notes or audit. Team responses omit global snapshot counts. Existing rules deny all direct client access and writes to attendance, snapshot and audit subcollections.

Commands check current account state, every canonical event/team reference, committed publication, active hierarchy, attendance rollout flag and effective resource closure. Cancelled/postponed events reject new attendance; a prior successful receipt can still acknowledge its original change after lifecycle changes, but only after live publication, team authority and enrollment checks. Same-request retries never write another revision. Removed entries with an existing attendance record remain correctable under live team authority; removed entries without attendance cannot acquire a new pre-completion record. Existing records are retained after removal. Rescheduling retains old revisions, shows current attendance as Unknown, and requires an explicit new observation with a reason.

## Completion and the Phase 3 interface

The existing `mutateEventSchedule` complete action now reads all retained roster entries before writing, then atomically creates one `events/{eventId}/rosterSnapshots/{participantId}` per unique participant, stores the completion marker on the event, and commits its normal lifecycle/history/outbox transition. At most 200 combined retained team roster entries are supported per completion, counted before deduplication. A larger roster fails atomically with an actionable bulk-completion limitation; no entries are truncated. This is a conservative transaction bound, not production capacity proof.

Each snapshot captures participant identity/display label, participant status, team IDs, per-team active/removed state, enrollment revision, joined/removed timestamps, schedule version, completion event revision, server timestamp and audit correlation. Eligibility is the active participant and active enrollment state at completion. Retained removed/archived entries are preserved explicitly and excluded from eligibility. Later transfers, archival, re-enrollment or account deletion do not change frozen eligibility. The event marker stores unique participant and eligible counts; server-side cross-team reports must count each participant once. The team-scoped callable exposes per-item frozen eligibility and the capture revision/time, so Phase 3 can sum all pages for the selected team without exposing the opponent's totals. Historical completed events without a snapshot return a null marker and an unknown denominator; this step does not fabricate a backfill.

`shared/attendance.ts` is the typed reporting interface. Consumers require completed events with a non-null snapshot marker, page the authorized team entries, retain source event/capture/schedule/attendance revisions and distinguish eligible, recorded, unknown and excused. Exclude cancelled/postponed events. Compute presence as `(present + late) / (present + late + absent)`, show unknown/excused/eligible totals separately, and use “not enough data” for zero denominators. Reports must detect later attendance revisions before reusing an exported result; report jobs, exports and stale-report rebuilding remain Phase 3 work.

Attendance history and snapshots are organization-owned operational records under the existing retention policy, like roster and schedule history. Deletion immediately denies the actor, removes their grants and command receipts, and retains event/participant history and audit actor IDs. No contact details, raw coordinates, device identifiers or account-owned projections are added. Retention/pseudonymization policy remains a release gate.

## Native behavior and release

Canonical event detail exposes Team attendance with separate intended/actual labels, explicit recording choices and correction audit. Reload and foreground refresh reauthorize, clear stale private content and reconcile the server. Unknown-result saves freeze their exact request ID/payload for retry; no offline queue is introduced. Loading, empty, denied, cancelled, stale and pagination behavior have focused rendered tests.

Deploy the new callables and verify snapshot array membership/revision pagination indexes in staging before client rollout. Enable `organizations/{orgId}.features.attendance` only through a separately authorized operator rollout. Completion snapshots do not depend on enabling manual attendance, so event history can retain an unknown denominator's inputs without manufacturing observations. Rollback disables attendance writes while keeping authorized reads and immutable history. P2.11 adds optional participant assertions and foreground location assistance through the same attendance storage; see [check-in assistance](check-in.md). No deployment, live flags, migration or provider integration is included.
