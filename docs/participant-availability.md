# Participant availability

P2.09 adds participant RSVP to canonical, committed published events. Families open Responses in the household calendar or canonical event detail. Each active enrolled participant has separate Yes, No and Maybe choices and an optional 240-character late-arrival note. A missing document means Unanswered. Availability describes intention and never writes attendance.

`getEventAvailability` discovers current household participants through the existing bounded canonical agenda sources and reads only their direct response documents. It rechecks household schedule access, participant status, every event team reference and active enrollment. A guardian additionally needs `respond: true` to save. Administrators explicitly enable that permission in guardian approval; existing grants and new invitations keep their existing defaults. Response permission requires schedule viewing and does not grant profile editing. Self-linked participants can respond for themselves while enrolled. Platform support and navigation pointers grant no tenant authority.

`respondToEvent` writes `events/{eventId}/availability/{participantId}` transactionally, comparing both the response revision and event schedule version. The caller cannot choose actor identity. A competing guardian save returns a conflict and requires a reload and review. Each successful revision also creates immutable `availability/{participantId}/history/{revision}` with the previous revisions retained. Receipts use existing account-scoped command IDs and deletion cleanup. Every replay reauthorizes current account, publication, household and enrollment access before returning its historical result. A replay after the deadline or reschedule acknowledges the earlier committed change; it does not apply it to the new schedule.

The current status is derived from the stored response's schedule version. A mismatch returns Needs reconfirmation plus the previous response, actor context and note; it is excluded from current Yes/No/Maybe totals until a fresh explicit choice is saved. Ordinary and reviewed makeup reschedules preserve the event ID and response history, increment scheduleVersion and reset any custom RSVP deadline to the new start. No bulk rewrite of response documents is needed.

Team totals are returned only for teams on which the caller has current staff/coach/captain authority. Families cannot list or filter another household's responses or notes. Each team counts unique active participants by deterministic roster document ID. Summary reads fail closed above 200 combined roster rows across authorized participating teams; supporting larger totals requires a paged summary design. This bound is not a production capacity claim. Direct client reads and writes to availability and history remain denied by the existing rules.

The deadline defaults to event start. Authorized every-team managers can choose one hour or 24 hours earlier, or restore event start, in canonical event detail. `setEventRsvpDeadline` enforces the event revision, hierarchy, publication and schedule fence, records an immutable policy history and accepts only a canonical UTC instant at or before start. Only scheduled, open-resource events allow policy edits. New responses close at the server deadline, on cancellation/postponement/completion, effective resource closure, or an archived enrolled team/hierarchy. A live access check also prevents withdrawn participants and deleting accounts from responding. Policy changes do not change the schedule version or erase responses.

Native response forms retain an uncertain save's exact request ID and payload for retry, disable edits during that uncertainty, and clear stale controls on conflicts or permission loss. Foreground refresh reauthorizes the panel; unmount and generation guards ignore late results. Reload reconciles server state before allowing another action. Offline edits are not queued or presented as accepted.

No migration, deployment, production data access or live flag changes are included. Existing canonical null-marker publication compatibility, legacy event screens, calendar subscriptions and account deletion remain intact. Participant history and audit actor IDs are retained with event history when accounts are deleted; user-linked grants, self links and command receipts continue through the existing deletion workflow. No contact data, delivery endpoint or new user-owned projection is created. This step does not implement attendance, reminders, provider delivery or offline caching.

Deploy the three callable endpoints before releasing clients that use them, verify the existing roster query/index and closure indexes in staging, and test organization rollout and deletion with synthetic data. Rollback disables new response and policy commands while retaining read/history paths; never reopen direct Firestore writes or erase historical responses.
