# Participant and guardian boundaries (Phase 1 Step 5)

These callable APIs add server-only organization-local identities. They do not expose household UI, enable organization flags, send invitations, deploy indexes or migrate live data. Keep `features.households` disabled until Step 6 expands account deletion and the later UI/rollout prerequisites are reviewed. New organizations still start with only `organizationV2` enabled.

## Authority and reads

Org admins manage independent participants, private profiles, explicit adult self-links and guardian approval/revocation. Program staff manage enrollment and read roster display fields only in their assigned programs. Organization-wide identity/private-profile edits are admin-only because participants have no canonical program ownership; a roster in one program cannot authorize editing the child's organization-wide identity. Active coaches/captains can read their assigned team's roster. Platform support, guardians and self-linked participants gain no roster management powers.

`listRoster({orgId, teamId, pageSize?, cursor?})` returns only participant ID, display name, jersey number, active status and roster revision. It omits account links, contacts, birth dates, guardian details and notes. Archived hierarchy remains readable to authorized staff/coaches; normal enrollment writes require active hierarchy. Removal remains possible after archive.

`getParticipantProfile({orgId, participantId, staffPrivate?})` uses current canonical self/guardian permission on every read. Household results contain public identity and birth date/participant contact fields; guardian contacts and staff notes remain admin-only through `staffPrivate: true`. Guardians need `viewProfile`; a schedule-only grant permits discovery but not profile reads. `features.households` gates household reads and edits, independently of granting authority. Canonical parent/grant reads occur inside the same transaction as the private read or edit, so revocation conflicts with in-flight transactions rather than relying on cached pointers.

`listMyParticipants({pageSize?, cursor?})` reads private candidate pointers and returns only live authorized participants. `listMyOrganizations` now recognizes canonical household relationships as well as staff. Both exclude unrelated/stale links. Pagination uses document-ID cursors and 1–50 candidate rows, so filtered pages can be empty with a next cursor. Organization discovery bounds guardian candidates at 11; if all are unavailable and more candidates may exist it returns `resource-exhausted` and directs the caller to paginated participant discovery instead of silently hiding later candidates. Direct Firestore reads/writes of participant, private-profile, guardian, roster and discovery paths remain denied, including to support users.

## Commands and revisions

All mutations require `requestId` and `expectedRevision`; retries use existing command receipts and recheck the actor's current canonical authority. Reusing an ID with another payload fails. Replaying an old success never restores subsequently revoked access or overwrites later edits. No name or email matching grants rights.

- `saveParticipant({orgId, participantId?, expectedRevision, fields})`: fields are `displayName`, `kind: youth|adult|unknown`, optional `externalId` and `status: active|archived`. New IDs are opaque. Creation expects revision zero. `linkedUserId` is server-owned. Same-name children stay separate. Archive removes this participant's discovery sources; restoration reestablishes currently approved sources.
- `saveParticipantPrivateProfile({orgId, participantId, expectedRevision, fields})`: full private fields are optional `birthDate` (validated local ISO date), `contactEmail`, `contactPhone`, `guardianContactDetails` and `operationalNotes`. Revision belongs to the private profile, starting at zero. Private field values are excluded from retry receipts and audit records.
- `approveSelfLink({orgId, participantId, userId, expectedRevision})`: an admin explicitly confirms an adult's own account, or supplies null to unlink it. Youth/unknown participants cannot acquire their own account through this command. Unlinking remains available after organization archive or rollout disablement. A current link must be removed before replacing it. A self-linked account cannot also be the participant's guardian. Migration-created existing links remain readable without being silently reinterpreted.
- `approveGuardian({orgId, participantId, userId, expectedRevision, permissions?})`: permissions default to `viewSchedule: true`, `viewProfile: true`, `editProfile: false`, `respond: false`. Respond is refused in Phase 1. Edit requires viewProfile plus server-owned `features.guardianProfileEditing`. Target account must exist and be available; no invitation/email flow is implied by this administrative approval.
- `revokeGuardian({orgId, participantId, userId, expectedRevision})`: retains a revoked audit record and immediately removes this participant's access sources. Revocation is allowed for archived organizations/participants, disabled organization rollout and unavailable target accounts.
- Both self-link and guardian commands check the **participant revision**, not the guardian-document revision. Responses return the new participant revision (`participant.revision` for self-link; `participantRevision` for guardian). Every grant/enrollment change increments participant revision and monotonic `accessRevision` in the same transaction.
- `setRosterEnrollment({orgId, participantId, teamId, status: active|removed, jerseyNumber?, expectedRevision})`: checks the **roster revision**, starting at zero, and validates participant/team org equality plus canonical hierarchy/program scope. It never changes coach/staff grants or creates guardian approval. The response includes `participantRevision` and `accessRevision`.
- `editParticipantProfile({orgId, participantId, expectedRevision, fields})`: self-linked participants and explicitly enabled guardians may edit only `contactEmail` and `contactPhone`. Revision belongs to the private profile. Omitted contact fields remain unchanged; explicit null clears only the supplied field. It preserves staff-only fields and rechecks live permission even on receipt replay.

## Atomic projections and operational bounds

Grant, roster and participant archive changes update canonical records, access revisions, private audit and discovery metadata in one Firestore transaction. `participantLinks` and `organizationLinks` are candidates only. Team pointers store separate `sourceParticipantIds`, so revoking one sibling cannot erase another sibling's access. Removing a household source also preserves unrelated fields in the pointer; future team/agenda readers must independently check canonical staff/self/guardian and enrollment records. A retained organization pointer never confers access.

Transactions support at most 10 active guardians and 20 active team enrollments per participant. They read one extra row to detect overflow and reject before writing. These bounds keep the complete projection fanout atomic; they are operational limits, not commercial entitlements. Oversized preexisting/migrated participants require a separately reviewed bulk access path before household rollout. New grants/enrollments cannot exceed the bounds. Unlinked participants can exist without Auth users; approvals never create accounts. Removed roster rows and revoked guardians remain for history.

Deploy/verify the checked-in roster and guardian collection-group indexes and participant self-link composite index before rollout. Other queries use collection single-field indexes and document-ID ordering. Emulator success does not establish production index readiness. The backend suite uses synthetic data only and includes direct rules denials, two organizations, program scope, two guardians, same-name children, revocation/replay/concurrency, sibling-source preservation, explicit self-linking, private response allowlists, rollout/account gates and atomic fanout-limit failures.
