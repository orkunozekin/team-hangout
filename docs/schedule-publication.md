# Resumable schedule publication

P2.07 adds deliberate publication to the existing browser schedule draft editor. `publishScheduleDraft` requires explicit confirmation, the saved draft revision, complete independently validated assignments, current staff/program/hierarchy access and the organizationV2/adminWorkspace/scheduler flags. It returns a durable operation; it does not send notifications. `getSchedulePublication` reloads progress. `advanceSchedulePublication` runs one bounded pass step with an expected operation revision and fencing token. Actions are advance, resume and abort. An uncertain result retries the identical request ID and payload; successful replay reauthorizes and returns current progress.

An organization has one `schedulingLock/current`. Its input revision serializes organization schedule mutations and its monotonic fencing token rejects stale workers. A two-minute expiry does not silently release an unfinished publication: authorized staff deliberately resume with a new token or abort. Catalog edits, hierarchy/team changes, event creation, compatibility edits/deletion, lifecycle changes, schedule-import row commits/publication and reviewed legacy migration transactions honor this fence. Draft mutations also honor it. All command stages share a transaction-local canonical document cache, so a facility scan reads one committed marker per operation rather than once per event. Staff revocation remains available; every publication call rechecks live authority, including replay. Coach/account deletion can change the snapshot and blocks further advancement until reviewed.

Batch bookings retain the effective availability revision and initial immutable resource history. The deterministic outbox records bounded division/team audience scope. The operation retains immutable deterministic event IDs, expected revision and payload hashes, a manifest hash, draft/input revisions and independent staging/promotion cursors. Each transaction stages at most 100 events or promotes at most 100 events. Promotion changes events to published while the operation remains uncommitted. The final transaction verifies the entire bounded expected event set, operation identity, revision, payload and published state, as well as current snapshot/input/fencing state. Cursor counts alone cannot authorize commitment. Only then does it atomically commit the marker and one deterministic organization outbox intent. The outbox has no trigger, provider or delivery worker in this step.

Every team list, event detail, household agenda, calendar feed and private event-information adapter requires a published event plus its committed operation marker. Existing server-owned null-marker single-event/legacy compatibility remains. Clients cannot choose or clear a bulk marker; canonical direct Firestore reads remain denied. Live authorized callable readers are the projection integration, so no new eventually consistent household copies are created. Team/agenda cursors bind the organization visibility revision: a publication commit between pages requires a fresh read. Team lists scan at most 500 candidates to fill a page past hidden events; agenda retains its existing 500 per-team/5,000 total scan limits. Overflow fails explicitly. Native consumers retain existing refresh/retry behavior.

Every advance re-reads current teams, canonical coach assignments, hierarchy/flags, resources/facilities, immutable availability, closures and committed occupancy. The snapshot hash binds current metadata/revisions, not just generated assignments. Own uncommitted events are excluded from self-conflict validation. Aborted events stay hidden, retained for operational history, and do not reserve resources. Abort releases the fence and draft pointer; edit and revalidate to create a new revision before another publication. Committed drafts remain immutable and linked to their publication. There is no automatic cleanup or external runtime dependency.

The original draft snapshot bounds remain conservative, including 1,000 tenant event documents, 1,000 assignment documents, 32 teams/resources and 5,000 query-result documents. Hidden/history documents count toward the event budget. Publication preflights existing tenant document count plus the complete expected batch, rejecting before lease acquisition/staging if recovery would exceed 1,000 event documents. A large tenant can be refused even for a small draft; nothing is truncated. Final verification reads all expected events (at most 992 round-robin fixtures) in one bounded transaction. These are pilot safety bounds, not measured production capacity. Real indexes, latency and transaction-size readiness remain staging gates.

## Verification boundaries

The product's complete round robin cannot have exactly 201 games. The real callable test rejects a 201-assignment partial and publishes a valid 210-game schedule through three staging and three promotion chunks. A separate trusted synthetic 201-event integration fixture bypasses round-robin creation only in test setup. It calls the same internal publication pass used by the callable against real emulator transactions and actual team/household/detail/feed readers, with 100/100/1 staging and promotion. Both cases simulate process loss during staging, during promotion and immediately before marker commit. Product complete-draft validation is never relaxed.

Tests cover exact uncertain retry, expired/stale fencing, revoked staff/replay, changed resource inputs, competing mutations, damaged payload verification, abort history, no precommit outbox/email and deduplicated postcommit team/household/feed visibility. Browser coverage exercises deliberate confirmation, lost chunk response, exact retry, reload, resume, promotion, explicit final commit and abort/edit/revalidate/restart without requiring focus or reload. The UI exposes progress and recovery without claiming a provider delivered anything.

No deployment, production access, migration execution, provider sends or live flag changes occur. Deploy compatible readers and declared indexes before enabling writers. Rollback disables scheduler writers and retains operation/event/history records. Recover or abort any held publication under authorized staff access. P2.08 closures and P2.13 notification delivery remain later steps.
