# Reviewed schedule imports

Schedule template v1 uses the existing private roster-import engine: strict UTF-8/BOM/quoted CSV parsing, explicit header mapping, immutable source bytes, 5 MB/5,000-row limits, bound preview and resolution revisions, resumable leased row commits, owner and program authorization on every transaction, private outcome export and configured retention cleanup. See [roster imports](roster-imports.md) for storage, retry, deletion and staging contracts. Roster and schedule command/job identities are separate; one kind cannot read or commit the other.

Required columns are teamExternalId, eventType (practice or match), title, localDate (YYYY-MM-DD), localStartTime/localEndTime (HH:mm) and timeZone (IANA). externalId is recommended. locationName, address and notes are optional. Both times are on the same local date; split overnight events or use a separately reviewed event command. startOffset/endOffset are optional signed HH:mm offsets. Nonexistent local times always fail. Ambiguous DST times require an offset that round-trips to the supplied local date/time/zone. A numeric offset alone never establishes a time zone. Invalid fields remain bounded, visible and skippable without changing the original bytes.

An external ID identifies an event within its organization/program/season. The deterministic private ledger preserves the same event ID across later imports, time changes and publication revisions. Team reassignment, other lifecycle states and deleted events require separate review. Repeated external IDs and exact source records must be skipped or corrected. A title without an external ID never merges events; an existing same-team normalized title requires an explicit choice to create a separate draft or skip. Name review is bounded to 1,000 team events; larger histories require trusted external IDs. New jobs without trusted external IDs intentionally create separate events. Existing-event overlap queries and same-team/date/zone civil-time source comparisons generate warnings; warnings do not block a valid import. Source warnings are conservative around different DST offsets, and neither cross-team scheduling nor automatic conflict resolution is provided. Excessive existing overlaps ask for manual review.

Commit writes scheduled, staged events only. Updating a published imported event makes it staged until separately published again; the preview warns about this visibility change. Drafts remain absent from household agenda and private ICS feeds. Each row's event, ledger and checkpoint commit atomically. Concurrent jobs and outside edits invalidate stale event/team revisions instead of overwriting them. Refresh only pending rows after a partial job; completed drafts retain their IDs.

Publication is a separate authenticated action after the import completes. Select up to ten successful drafts on the current page, review actual stored titles, times, zones, locations, draft revisions and queued-contact counts, then explicitly confirm. A server-derived binding covers the exact event revisions and current verified household recipient identities/email addresses. Publication rechecks job ownership, flags, active hierarchy/team scope, current drafts and recipients. A changed draft or recipient set requires a new review. Replay returns the saved result only after canonical owner/scope checks. Publication and its outbox entries commit atomically, so double-clicks, lost responses and retries cannot create another revision or another queue for the same event revision/recipient. The UI retains uncertain requests across polling and focus.

Recipient selection follows canonical active team roster, participant, guardian viewSchedule/self relationships and available accounts. Only verified, enabled Auth accounts with an email are queued, deduplicated by account identity. Imported email strings, stale projections, unrelated users and revoked/deleting accounts establish no recipient rights. Limits are 100 active roster records per event, ten guardians per participant and 200 essential updates per publication transaction; larger scopes fail before publishing and need a reviewed bulk workflow. Confirmation returns counts without exposing household addresses to staff.

Server-only emailOutbox entries use kind publishedEvent, orgId, eventId, eventRevision, recipientUid/recipientEmail, queued state and initial retry metadata. Their deterministic key is purpose/event/revision/recipient. No transport, scheduler, sender domain, secret, production flags or live send is configured here. Step 14 must reauthorize recipients, suppress unavailable/bounced contacts and stale event revisions, resolve safe time/place content and implement transport idempotency/failure handling. A queued record does not mean delivery or receipt. Event updates may leave prior revision records queued; they must be suppressed if stale before sending.

Before exposure, verify declared overlap/name-review indexes in staging, import worker/Storage configuration, retention policy, recipient limits, scale and recovery. Hosted calendar clients, complete iOS subscription, production sender/provider/privacy approvals, rollout, migration and live delivery remain external gates.
