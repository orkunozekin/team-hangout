# Household and roster UI (Phase 1 Step 8)

Native Household is available to signed-in accounts with or without a legacy team. Teams retains the existing coaching/join/create flow. Household discovery follows every candidate page and rechecks canonical self/guardian relationships. Choosing a participant loads the authorized profile independently of coaching roles. The screen shows the signed-in account, selected participant, approved guardians and whether contact editing is allowed. Saving confirms the account and participant; birth date is read-only, and only approved contact fields can be edited. Permission failures discard the profile and refresh discovery. Account changes, leaving Household and backgrounding discard household screen state. Returning reloads canonical permissions. No household profiles are persisted by these screens.

`getParticipantProfile` now returns `relationship`, `canEdit` and active guardian display names with a `isYou` marker. Household guardian summaries exclude UIDs, contact details and permissions. Admin private reads additionally return guardian UIDs/rights for explicit approval/revocation. Names come only from accounts already canonically approved for this participant. The read authorizes first, checks grants in the same transaction and keeps the ten-guardian operational bound. Coach `listRoster` responses retain their exact display-only allowlist.

The browser route `/organizations/:orgId/participant?program=:programId` uses the existing staff workspace gate. Organization admins create/edit/archive independent participants, edit private profiles, approve confirmed existing guardian UIDs with default view-only rights and revoke guardians. No matching by name/email or invitation sending occurs. Program staff see only assigned-program teams and display-only roster fields. They may enroll a confirmed organization-local participant ID, change jersey numbers, remove and restore enrollment. They cannot enumerate organization-wide participants or open private profiles. All mutations use loaded revisions and stable IDs for uncertain retries. Focus rechecks preserve edits when authority is unchanged; scope changes/denial discard data. Auth transitions unmount the entire workspace.

`listOrganizationParticipants({orgId,cursor?,pageSize?})` is admin-only and returns public identity fields and revisions, including archived identities, with max page size 50 and document-ID pagination. `listRoster({includeRemoved:true,...})` is staff-only and returns display fields for removed rows as well as active ones, allowing restoration with the current enrollment revision. Coaches cannot request removed history. No new indexes are needed beyond collection/document-ID single-field indexes. Deploy the new callable and updated profile/roster handlers before exposing the UI. Server-owned household/workspace flags remain disabled unless explicitly enabled by the operator after release prerequisites.

## Local verification

Use the isolated demo emulators as described in `docs/backend-testing.md` and `docs/browser-admin.md`. `scripts/seed-household-demo.mjs` refuses any non-demo project or non-loopback emulator addresses. It seeds two distinct children, two authenticated guardians, a parent with a retained legacy coaching team, a scoped staff account and a separate admin. Synthetic credentials are local fixtures only. Browser tests invoke it automatically; a manual native evidence session can invoke it with `GCLOUD_PROJECT=demo-team-hangout FIRESTORE_EMULATOR_HOST=127.0.0.1:8080 FIREBASE_AUTH_EMULATOR_HOST=127.0.0.1:9099 node scripts/seed-household-demo.mjs` while these emulators run. Never use it against a live project.

Backend fixtures assert guardian-summary/private-profile boundaries, admin-only discovery, staff history, restoration and canonical revocation. Native interaction tests cover two-child context selection, view-only versus editable profiles, acting-for save confirmation and revoked save cleanup. Browser tests cover creation, private edit, removal/restoration, scoped roster privacy and access removal. Actual device/browser captures supplement these tests. Invitations (Step 9), combined agenda (Step 10), live rollout and migration remain separate work.
