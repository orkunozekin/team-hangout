# Household agenda (Phase 1 Step 10)

`listHouseholdAgenda` is an authenticated, read-only callable. The native Household calendar uses canonical v2 instants; the existing single-team Schedule and event editor retain their legacy behavior. Deploy the callable and checked-in indexes before exposing this calendar. No rollout flags, production data or deployment are changed by this implementation.

## Scope and privacy

Canonical guardian/self queries discover personal participants, including migrated self identities without navigation pointers. Organization navigation links nominate staff candidates, never establish access. In one read transaction, the server rechecks the actor's deletion state, organization rollout flags, active participant and guardian `viewSchedule` rights (or explicit self-link), active roster enrollment, hierarchy integrity, scoped staff membership and coach/captain assignments. Staff sees only assigned programs; platform support is not a household grant. A two-organization guardian sees both through separate personal grants. Staff access does not attach roster names: participant labels come only from the caller's own approved personal relationships. No birth/contact data, notes, roster directory, other guardian identities, or unauthorized opponent team identifiers enter the response. Direct agenda/event Firestore access remains denied.

Only `schemaVersion: 2`, scheduled, published, non-deleted events with valid start/end timestamps and timezones enter results. All referenced teams must match the event's organization/program/season/division contract. Non-null publication operations remain excluded until a later phase implements committed publication fences. Staged migration events stay invisible. Archived hierarchy/team context is excluded by default; include it explicitly to view history in the selected window. Draft seasons are also excluded by default. Cards include authorized team/organization/season context and both display and event timezones. A legacy-membership notice and persistent setup guidance direct unresolved legacy schedules to Teams and administrator time confirmation/publication.

## Query and pagination

Requests carry ISO UTC `from` (inclusive) and `to` (exclusive), a window no longer than 93 days, and page size 1–100. Optional participant, team, organization, season and event-type filters only narrow canonical access; unsupported/foreign filters return no events. Empty filter arrays mean all accessible values. Participant and season references always include the organization ID.

The server queries authorized teams individually with the checked-in composite event index: organization, team array membership, deletion, publication, scheduled lifecycle and start time, ordered by start time then document ID. Each stream contributes enough valid events for the requested page plus lookahead; streams merge by exact Firestore seconds/nanoseconds and event ID, deduplicating shared events and participant labels. Cursor timestamps preserve sub-millisecond precision. Cursors bind caller, normalized request, and current accessible team/label context; an access or filter change returns `AGENDA_CHANGED` and the client discards loaded pages. They are ordering hints, not authority or a snapshot guarantee: concurrent event edits/inserts can change later pages and Reload starts a fresh traversal.

Fanout is bounded at 100 personal source rows per collection, distinct personal identities, organization discovery links, memberships, teams and staff program scopes, 20 rosters per participant, 500 scanned event rows per team, and 5,000 total scanned rows per request. Limits fail explicitly with `resource-exhausted`, never silently truncate. These limits are an initial safety envelope, not a proven production-scale claim; large organizations need a reviewed projection/bulk read design. Transactional reads avoid combining a revoked grant with a later event response. Staging must verify index readiness, latency, and the intended pilot's scope before rollout; emulators do not enforce production indexes.

## Native state and dates

The calendar defaults to a 30-calendar-day window starting today in the device's IANA timezone. Date/timezone controls convert local calendar boundaries to UTC instants, including DST transitions and skipped-date validation. Cards format the canonical start/end in that display timezone and retain the event timezone. Filters are memory-only preferences. Unavailable participant/team/organization/season selections are removed after reauthorization. Loading, no matching published events, setup-required, transient connection errors and access-change errors have separate states. Each successful first-page calendar read also refreshes surrounding participant discovery through a separate generation, including individual revocation that returns success with fewer participants. Reload and Load more reauthorize; delayed responses cannot restore obsolete pages. Account changes, leaving the Household tab, or backgrounding unmount the calendar and discard its private state. There is no offline authorization, persistent calendar cache or guaranteed background synchronization.

## Validation

`yarn typecheck`, `yarn test --runInBand`, and `yarn test:backend` cover sibling/multi-team deduplication, personal two-organization scope, program staff isolation, unrelated filters and forged pointers, publication/lifecycle/archival gates, revocation between pages, deletion, self/coach access, equal starts and sub-millisecond ordering, half-open date bounds, 23/25-hour days, Lord Howe transitions, skipped dates, distinct fold offsets, delayed UI responses and error/empty/setup states. Run native evidence against this checkout's Metro server and explicit `demo-team-hangout` loopback emulators; web rendering is not native proof. ICS subscriptions remain Step 11.
