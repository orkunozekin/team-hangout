# Reviewed roster imports

Roster template v1 accepts UTF-8 CSV with a BOM, quoted commas, doubled quotes and multiline fields. Limits are 5 MB and 5,000 nonempty records; malformed UTF-8/quotes/headers/row shapes fail without truncation. Map headers explicitly. Required fields are participantName, kind and teamExternalId. externalId is strongly recommended; guardianEmail1/2 are optional. Private birth/contact/profile data are outside this template.

Set a team's optional external ID in the Teams editor before uploading. The server requires exactly one matching active team in the selected organization/program/season. Duplicate external IDs in a file and exact duplicate records are errors; skip explicitly or correct and upload again. Existing trusted participant external IDs select an update. Names, including normalized older names, only propose candidates; explicitly match an active candidate or create a separate identity. Name-only discovery is bounded to 5,000 organization identities; larger organizations must supply trusted external IDs. Reusing the file under another job does not merge identities by name.

Organization admins may create/update identity and roster data. Program staff may import enrollment for an existing trusted identity already active on that selected roster, preserving identity fields. This retains the established admin-only participant identity boundary; imports do not confer broader identity authority. Out-of-program/tenant targets, archived hierarchy, disabled imports and deleted owners are rejected. Current canonical authority and revisions are checked in every row transaction.

The upload callable authenticates, authorizes, parses the exact bytes and saves an immutable private Storage object at imports/{orgId}/{jobId}/source.csv. Direct Storage and Firestore job/row access are denied. No download tokens or public objects are created. A hash binds the upload request to bytes, mapping, template, program, season and policy revision. The confirmed preview revision and binding fence commit. Callable receipts contain no source bytes or row contacts.

Preview writes only private job/row records, never participants, roster, grants, invitations or mail. Every invalid or ambiguous record needs explicit resolution/skip. Commit is asynchronous, with a two-minute lease, batches of at most 25 row transactions and an atomic per-row checkpoint/outcome/operation ledger. Completed rows remain committed after partial failure. A stale record stops with needs-review; revoked authority pauses. Refresh discards pending resolutions and re-previews only unfinished rows against current canonical data. Reconfirm before continuing. Trigger retries and the five-minute sweeper recover expired leases. A later permission restoration never silently resumes a paused job.

Save the displayed job ID to reopen after navigation. All reads reauthorize. Browser temporary failures preserve file/mapping and uncertain actions retain their request IDs; confirmed permission loss clears tenant state. Outcome CSV includes every recorded result and escapes spreadsheet formula prefixes. Guardians are never activated by import. After completion, the optional row invitation action explicitly confirms the acting account, participant, email and view-only rights through the existing invitation command. Its deterministic job/row/contact request ID prevents duplicate queues on retry/reload. The Invitations screen provides normal resend/revoke controls. Only that separate confirmation queues an invitation outbox entry. Imports send no mail.

IMPORT_BUCKET selects the private bucket; the fallback is the current Firebase project appspot bucket. Verify the real bucket name before staging (newer projects may use firebasestorage.app). IMPORT_RETENTION_DAYS is configurable from 1 to 30 days, default seven. A daily bounded cleanup deletes expired raw objects, nested preview/outcome rows and jobs; the expiry timestamp is not a claim of immediate physical deletion. Account deletion fences the owner first and marks import source/rows for expedited next-cleanup removal. Completed organization identities/rosters and the non-contact operation ledger remain under organization retention policy. Pending source data have no client access after owner deletion.

Before exposure: owner approves retention/minor contact policy, bucket/service permissions, storage rules, indexes, trigger/scheduler deployment, imports flag and staging recovery/scale rehearsal. The 5,000-row throughput target and real staging Storage/index behavior remain Step 15 gates. No production migration, flag enablement, sender change, transport send or deployment is authorized by implementation.
