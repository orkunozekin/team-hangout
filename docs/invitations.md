# Scoped household invitations (Phase 1 Step 9)

Organization administrators issue invitations for an existing organization-local participant, either as guardian with explicit approved permissions or as a confirmed adult linking their own account. Program staff and coaches cannot approve organization-wide identity or guardian rights. An optional team context must be an active same-organization enrollment with valid active parents; accepting does not enroll a participant, assign coaching authority or create an identity. Legacy team codes remain separate.

## Commands and security

`createInvitation` takes `requestId`, `orgId`, `participantId`, optional `teamId`, `recipientEmail`, `relationship` (`guardian` or `self`) and four explicit permission booleans. `respond` is always false in Phase 1; contact editing requires the existing server flag. Guardian invitations from the browser default to view profile/schedule only. Adult self invitations disclose profile/schedule viewing and contact editing, matching the existing self-link policy; they do not depend on the guardian-editing flag. Issue and acceptance require active hierarchy, `organizationV2` and `households`; this PR enables no live flags. All issuance, listing, resend and revocation operations recheck canonical organization administration. No role is inferred from email equality.

`resendInvitation` and `revokeInvitation` take invitation ID and loaded `expectedRevision`. Resend keeps the relationship and recipient immutable, invalidates the old hash and cancels its outbox payload atomically. Default expiry is seven days from issuance/resend. Revocation remains available while rollout is disabled or the organization is archived. Accepted invitations cannot be resent or revoked; revoke their actual relationship in the participant profile instead. Completed issuance requests return their historical status/revision without generating another token, but still reauthorize the current administrator.

Raw tokens are 32 random bytes encoded as case-sensitive base64url. Only SHA-256 hashes enter `invitationTokens/{hash}` and private invitation records. Tokens never enter receipts, audit records, list results, application logs, browser storage or screenshots. The one delivery copy is an AES-256-GCM encrypted envelope in server-only `emailOutbox/{invitationId}_{revision}`. Configure Secret Manager `INVITATION_DELIVERY_KEY` to a cryptographically random 64-character hex key before live issuance. Retain that key until queued envelopes are delivered or cancelled; a key change needs explicit handling of the queued generation. The exact `demo-team-hangout` Functions emulator uses a public synthetic test key only; no live deployment falls back to it. Deploying Functions with this secret requires its prior setup.

The outbox contract contains `kind`, org/invitation IDs, recipient email/optional recipient UID, `status: queued`, encrypted `payload` and expiry. There is no transport worker in Step 9 and no message is sent. Step 14 must decrypt only at delivery, recheck current invitation token/status/expiry, rollout, participant access revision and inviter authority, select the approved HTTPS origin, and safely update transport status without logging the token. Transport acceptance is distinct from user acceptance or reading. Resend/revoke/accept cancel queued envelopes. No automated retry may deliver an old generation. Invitation lists expose separate invitation and delivery status; a worker must synchronize delivery status when added.

`inspectInvitation({token})` and `acceptInvitation({token, confirmed:true})` require sign-in. Before exposing a participant name or granting rights they use current Firebase Auth email verification and matching normalized email, an available account, live inviter administration, rollout, current participant and optional team scope. A changed participant access revision requires an administrator-reviewed resend. Existing guardian permissions are never overwritten by an older invitation. Concurrent accepts commit one relationship; successful replay is informational and never recreates a subsequently revoked grant. Unknown, expired, replaced, revoked and already-used links expose no participant details. Deleting identities fail closed through the existing durable tombstone, including cached tokens. Nested invitations bound to a recipient UID are included in account cleanup with their current token/outbox. An invitation issued before any Auth account exists is bound to its verified recipient at acceptance; invitations are not retroactively adopted through a deleted account's UID.

All invitation, token, outbox and audit paths stay denied to direct clients. Invitation lists page by document ID, max 50. The checked-in collection-group `invitations.recipientUid` index supports account cleanup; no other new composite indexes are required.

## Browser and native acceptance

Links use `/invitation#token=<opaque-token>` on the approved HTTPS browser origin, or `teamhangout://invitation#token=<opaque-token>` for the installed app. Fragments avoid sending bearer tokens in HTTP requests and referrers. The browser removes the fragment immediately and holds the pending token in memory through initial login. Reload after removal requires reopening the original link. Explicit logout or an account switch clears it; the user must reopen the original invitation with the intended account. Confirmation is always required. Existing codes still uppercase; invitation links never use that parser.

The browser acceptance route works without admin workspace access or native installation. It offers email/password sign-in, invitation-only household account creation, password reset and verification-email recovery. The normal admin login has no registration button. New browser household profiles follow the existing self-create Firestore allowlist with a fixed user role and no active team. The native app uses its existing auth/registration flow and displays the invitation after login. Both show the current account, approved relationship/rights, a confirmation action, non-sensitive terminal states and organization-help guidance.

The HTTPS Hosting origin, Auth authorized domain and iOS/Android domain association are owner-controlled deployment gates. No domain is guessed, native association is not claimed and no production deployment is performed here. Custom-scheme support and browser fallback can be tested locally; actual universal-link cold/warm association requires the approved domain and a rebuilt native binary. No mail delivery or deployed-link verification is claimed.

A resend binds the new generation to the current approving admin and preserves the original creator metadata. Inspection and acceptance share access-revision and guardian-editing checks; changed scope returns `needs-review` with reviewed-resend guidance before confirmation. Browser access denial invalidates pending list results.
