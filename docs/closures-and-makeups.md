# Closures and reviewed makeups

P2.08 adds Closures and makeups to the browser workspace. Organization administrators preview an explicit UTC interval and selected active resources, or all active resources at a facility. Shared closures can affect every program, so program staff cannot apply them. Makeup review accepts current staff with the event program grant and authority for every participating team. Platform support, navigation pointers and household access grant no operational authority. Every request and receipt replay rechecks current access.

`previewFacilityClosure` stores a bounded impact preview with canonical event revisions and an input hash. `applyFacilityClosure` requires that preview hash and explicit staff confirmation, re-reads current inputs, and rejects a changed preview. The apply transaction immediately creates the authoritative applied closure, durable operation, scheduling fence, audit and deterministic outbox intent. Event writes have not yet happened. Authorized family/team/detail reads already show affected scheduled events as postponed; the original interval/history remains. Scheduled-only calendar feeds exclude them. Private game-day information and resource assignment reject closed intervals. New resource assignments and reschedules check the full setup/cleanup interval against closures.

Closure intervals are half open. An event beginning before midnight or before the closure boundary is affected when its occupied interval overlaps, including cleanup. A touching boundary does not overlap. Resources are qualified by facility identity in both closures and scheduler validation. One whole-facility apply resolves the complete active resource set within the bound; no page or array is silently truncated.

`advanceFacilityClosure` processes one expected event in each bounded transaction, with expected operation revision and fencing token. It atomically postpones the event, retains immutable schedule/resource history, writes audit/outbox intent and advances progress. Other schedule mutations honor the P2.07 organization fence. Expiry never reopens the interval or releases an unfinished operation. Staff explicitly resume with a new fencing token. Failed transactions do not advance; lost responses retry the identical request ID and payload, reauthorize and return current progress. Reload by operation ID supports recovery after browser/process loss. The browser does not automatically run a background worker.

If a trusted maintenance change makes an expected event differ from the reviewed revision or interval, the operation records its ID as requiring reconciliation, advances without overwriting it, and reports the mismatch separately from postponed count. Completing the pass releases the scheduling fence while the closure stays authoritative. Staff must inspect mismatch events and explicitly postpone or reschedule them using current revisions. No all-events-atomic claim is made.

`previewEventMakeup` reviews a specific postponed event at a chosen active resource and UTC interval. `confirmEventMakeup` requires explicit staff confirmation and the preview hash, then revalidates current hierarchy/grants, season dates, resource sport/state/effective availability/buffers/closures, team overlap and current canonical coach overlap. Publication-created events retain the immutable source draft duration, team blackouts and minimum rest policy. Single-event compatibility records preserve their existing duration and use overlap-only rest policy (zero additional rest); no new organization policy is guessed. Cross-organization coach conflicts remain explicitly not checked. Confirmation participates in the same scheduling mutation fence and input revision as publication and preserves the event ID, original interval, schedule history and schedule version. Availability responses/reconfirmation remain P2.09.

## Bounds and release

Closure preview resolves at most 1,000 facility resource documents and scans at most 1,000 facility event documents, including history/hidden records. Each facility closure read scans at most 1,000 closure records once per transaction attempt, shared by up to 50 team rows or aggregate/feed scans. The cache is never retained across transactions or revocation. Preview payloads above 750 KB are rejected before persistence. Closure ranges are at most 16 weeks. These are conservative pilot bounds, not production capacity evidence.

Makeups query at most 1,000 tenant event records intersecting the proposed interval plus reviewed rest, and at most 1,000 active tenant assignment records. The event query uses both canonical endsAt and startsAt bounds, avoiding cumulative historical-event reads; overflow fails explicitly. The declared composite index needs staging verification. Current resource reservation validation retains its existing 500-candidate limit and fail-closed behavior.

No provider sends, weather automation, notification worker, production data access, deployment, migration execution or live flag changes occur. New organization-owned previews, closure records and progress retain operational history; user request receipts remain covered by existing account deletion. Compatible readers and all six new callables plus the declared index must be deployed together before using the workflow. Rollback disables new operations and retains closure/read/history guards; do not remove an applied closure to recover a failed event pass. Resume under current authorized staff access.

The owner also requested readable app dates and times during this step. Browser impact and makeup summaries, facility availability history, recurrence occurrences and schedule choices use the shared readable date/clock formatter. Event timezone labels distinguish repeated DST hours. Calendar-only dates retain their stored day. Partially edited values do not crash rendering. Closure authoring uses readable date/time picker controls explicitly labeled UTC. Other authoring fields and CSV source values retain their explicit input formats; stored UTC instants and mutation payloads are unchanged.
