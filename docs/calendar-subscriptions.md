# Private calendar subscriptions (Phase 1 Step 11)

The native Household entry and browser `/calendar-subscriptions` manage private, read-only RFC 5545 iCalendar URL subscriptions. They use the same authenticated account; browser calendar management does not require staff access. Importing a downloaded `.ics` file creates a one-time copy, not a subscription. Apple Calendar, Google Calendar, Outlook and other clients with URL subscription support can consume the standard feed; a claim of universal calendar-client compatibility requires actual interoperability evidence, not merely generating an ICS file.

## API and authorization

`calendarSubscriptionOptions({})` lists currently eligible active teams and approved personal participant labels. `createCalendarSubscription({requestId, teamIds, participantRefs?, eventTypes?, includeParticipantNames?})` requires 1–20 explicit teams, at most 20 specific organization-local participant references, and at least one event type. Omitting participant references selects the chosen teams' schedules without participant labels. Names default off; including them requires explicit participant selection and UI confirmation explaining provider/bearer access. Each selected participant must still have personal schedule access and an active enrollment in a selected team. Each selected team must match the participant filter when provided.

Scope is immutable: new teams/enrollments/participants cannot broaden an existing URL. Create another subscription after explicitly reviewing a new selection. Rotation preserves exactly the old selection. `rotateCalendarSubscription({requestId,subscriptionId,expectedRevision})` atomically revokes the old URL and creates a replacement. `revokeCalendarSubscription({requestId,subscriptionId,expectedRevision})` remains available to the owner after grant loss, season archival or flag rollback and tolerates completed removal retries. `listCalendarSubscriptions({})` returns at most ten active, owner-only metadata records without bearer URLs. Management metadata is the caller's saved selection; it does not assert continuing schedule access. Another user cannot list, rotate or revoke it.

Issuance uses a cryptographically random 256-bit bearer, returned once. `calendarSubscriptions/{sha256}` holds only owner UID, exact scope, version/revision and creation/update/revocation timestamps. Command receipts also contain metadata only. A replay rechecks current authorization and returns `url: null`; rotate to recover a lost response or forgotten URL. Native/browser uncertain actions retain their exact request ID and payload; retry never creates a second feed. Deletion's existing `calendarSubscriptions/ownerUid` and `commandRequests/uid` cleanup hooks remove records, while its durable tombstone denies feeds immediately.

`calendarFeed?token=...` accepts GET/HEAD and independently rechecks subscription state, account tombstones, live guardian/self/team/staff authority, current enrollment, active hierarchy and all selected organizations' flags inside the same read transaction as event queries. Losing any required selected access invalidates the whole feed with HTTP 404 and generic `Feed unavailable.` text; it never returns partial private data on permission failure. Invalid/revoked tokens use the same response. Operational errors/size ceilings return 503 without an ICS body, rather than a misleading truncated calendar.

Canonical authorization/discovery and event filtering reuse `calendar/agenda.ts`. Public agenda inputs retain their 93-day limit. The internal feed query spans rolling UTC instants from 30 days ago (inclusive) to 365 days ahead (exclusive), active seasons only, and at most 499 events. Existing per-team/total scan and access fanout limits also apply. Exceeding them requires a narrower selection, not silent truncation. Only valid v2 scheduled, published, non-deleted events without pending publication operations enter feeds. Staged, legacy, archived and malformed events remain excluded. Each event appears once even across sibling/team selections.

## Format and privacy

The feed uses UTC DTSTART/DTEND, stable `eventId@CALENDAR_UID_DOMAIN` UIDs, event revision SEQUENCE, canonical modification timestamps, CRLF, TEXT escaping and 75-octet UTF-8 folding without splitting code points. Fields are allowlisted: title, selected team labels, location, instants, UID and revision; approved selected participant names appear only by opt-in. Staff notes, profiles, contacts, birth dates, roster lists and other guardians are excluded. The domain must remain stable after release or clients may duplicate events. Calendar timezones display according to the recipient calendar; UTC instants preserve DST offsets.

Every success/error response sends `Cache-Control: private, no-store, max-age=0`, Pragma/Expires, `Referrer-Policy: no-referrer` and `X-Content-Type-Options: nosniff`. No ETag, public CDN cache, application request URL logging or diagnostic bearer values are introduced. Browser URLs are displayed only after successful issuance and discarded on navigation, account changes, hidden-tab transitions or reload. Native management unmounts on leaving Household/backgrounding/account changes. No feed URLs or participant calendar state are persisted in client storage.

A URL is a bearer credential: anyone receiving it, including a calendar provider, can fetch its selected schedule. Revocation stops new server reads; calendar apps choose their own refresh timing and can keep previously downloaded entries. Remove the subscribed calendar in the calendar app too. Rotation requires replacing the URL in that app. No immediate remote deletion or background refresh guarantee is made.

## Deployment gates

No production data, flags or deployment are changed by this step. Before exposure:

- Configure a stable public HTTPS `CALENDAR_FEED_BASE_URL` ending at the function/approved rewrite, without query, fragment or credentials; configure stable `CALENDAR_UID_DOMAIN`. Emulator defaults exist only with `FUNCTIONS_EMULATOR=true` and exact demo project.
- Deploy commands, HTTPS function and the owner/revocation composite index, and verify index readiness. Direct client access to subscriptions/receipts stays default-denied.
- Configure infrastructure logging exclusions/redaction for this endpoint's bearer-bearing request URLs, including Cloud Run/load balancer/CDN/proxy/access logs and third-party tracing. Application log redaction cannot sanitize infrastructure logs. Verify with synthetic tokens before enabling subscriptions; do not enable a public caching layer.
- Enable server-owned `features.calendarSubscriptions` only alongside canonical household/v2 rollout after staging validation. Rollback disables feed reads and fresh issue/rotation while leaving owner removal available.
- Subscribe in actual calendar clients, inspect initial content, edit/revision refresh and post-revoke behavior. A localhost feed cannot be fetched by Google/Outlook cloud servers. Public HTTPS hosting/domain and real-client refresh measurements remain external gates until an approved staging endpoint is provided.

## Validation and client evidence

Run `yarn test:backend`, `yarn typecheck`, `yarn test:coverage --runInBand`, normal browser build and `yarn test:admin`. New emulator tests cover escaping/folding, stable UIDs/sequence changes, bounded/lifecycle filters, absent private data, token-free storage/receipts, replay, foreign scope/ownership, rotation, removal, rollout rollback, participant revocation/enrollment and account tombstones. Native tests cover minimal selection/confirmation, retry identity and late-response disposal. Browser tests use actual Auth/callables and feed HTTP responses, including a dropped response, hidden-tab race, account switch and mobile overflow.

Actual client subscription and refresh observations, inspected UI captures and any missing evidence are recorded in the step PR and feature handoff. An HTTP test or file import must not be reported as an actual calendar-client subscription.

### Local interoperability observations (2026-10-13)

- macOS Calendar subscribed to the synthetic loopback feed as an On My Mac calendar. Manual refresh updated the existing event title with the same UID and increased SEQUENCE, without duplication. Its default automatic refresh was weekly; the test selected five minutes, but did not measure a timed background refresh. After revocation the server returned generic HTTP 404 with no event data, while Calendar retained its downloaded event after manual refresh. The synthetic subscription was then removed locally.
- iOS 26.5 Calendar on iPhone 17 Pro parsed the URL and showed the correct synthetic event and time in its subscription preview. The final subscription confirmation control was absent from accessibility output; coordinate input failed with `noWindowsAvailable`. A completed iOS subscription and refresh were not verified. The preview capture is evidence of parsing only.
- Google Calendar and Outlook cloud subscriptions cannot fetch the loopback endpoint. Their real subscription/refresh verification, completed iOS subscription, and infrastructure log-redaction verification remain staging gates. Standards-compliant ICS supports clients offering URL subscription; compatibility with every calendar application is not asserted.
