# Facilities and resource availability

P2.03 adds Facilities and resources to the existing browser workspace. Organization administrators create and edit shared facilities and exact field/court identities. Active program staff with a live active program grant can read the safe organization catalog. Coaches and households cannot enumerate it; event readers retain the safe assigned location snapshot. Platform support and discovery pointers grant no tenant authority. Direct client reads and writes remain denied.

Facilities have an explicit IANA time zone, address, optional coordinate pair, parking/accessibility instructions and active/unavailable state. A keyboard-accessible map link opens the supplied coordinates or address without requesting the user's location. Resources have a stable identity, exact label, supported sports (soccer, basketball, football), setup/cleanup minutes from 0 to 180 and active/unavailable state. Use one resource identity for one shared physical space. Unavailable state preserves records rather than deleting history. Immutable facility/resource `revisions` snapshots retain state, sport and buffer changes with effective server timestamps for later historical utilization.

## Availability revisions

`appendResourceAvailability` appends immutable revisions under the resource's `availability` subcollection, with the resource's expected revision, request ID, explicit UTC `effectiveFrom` and at most 100 explicit `[startsAt,endsAt)` windows. It never generates recurrence. New revisions take effect in the future, strictly after the preceding revision. An empty window list explicitly means unavailable. Past revisions cannot be rewritten. The form accepts one `2035-01-02T12:00:00.000Z,2035-01-02T23:00:00.000Z` pair per line; it never guesses a time zone or DST offset.

The validator selects the effective revision for the entire occupied interval. A revision boundary cannot split an occupied interval. Adjacent windows are continuous; gaps and overlapping input windows are handled explicitly. Adding availability cannot invalidate an existing active reservation, including cleanup crossing an effective boundary. Resource sport/state changes and facility unavailability likewise reject incompatible future reservations. Move or postpone affected events first; closure operations remain P2.08.

## Event assignment and occupancy

The staff view loads an existing published event by ID and assigns the selected facility/resource through `mutateEventSchedule`. Authority is checked for every participating team, independently of catalog access. `createEvent`, single-event staged promotion through `updateEvent`, and lifecycle rescheduling validate the same resource contract. Schedule CSV preview/commit/publication reject resource-assigned events so they cannot silently replace occupancy or history. Legacy events without resources retain their existing behavior.

Resource bookings are limited to 24 hours, with setup and cleanup extending occupancy. Intervals are half open: touching occupied boundaries are allowed; a one-millisecond overlap is not. Resource identity, exact facility/field label, original buffers, effective availability revision and occupied instants are stored as snapshots. Buffer/label changes apply to new assignment or rescheduling; unrelated detail edits preserve the booking snapshot. Assigned resources determine location; custom location changes require removing the resource assignment. Assignment can be removed through the lifecycle edit API with both IDs null.

Published scheduled and completed events occupy their interval; staged, postponed, cancelled and soft-deleted records do not. Postponement/cancellation release active occupancy and preserve immutable `resourceHistory` and `scheduleHistory`. Completion preserves historical occupancy without inferring attendance. Rescheduling retains event identity and revalidates current resources. Availability and occupancy metadata remain server-only; event readers receive the existing safe location name/address and resource identifiers. Staff catalog responses exclude actors and audit metadata.

Assignments read the canonical resource and write a resource fence in the same transaction as the event, receipt, audit and history. Concurrent assignment and catalog changes retry against current data. Collision discovery reads at most 501 candidates across a bounded start range with a 27-hour lookback (24-hour event plus 3-hour cleanup) and 3-hour setup lookahead. More than 500 candidates fails closed with an explicit limit; it never silently truncates. Availability/catalog changes also cap reservation validation at 501 documents. Catalog and revision reads are explicit pages of at most 50; the new UI performs one request per Load more action and retains prior rows on errors.

## Validation and release

Run `yarn test:backend` (or `yarn test:operations`, which includes facilities and account deletion), `yarn test:admin`, native typecheck and unit/component tests. Always check the Functions build exit before starting emulator tests. Tests exercise live callable authorization, revoked receipt replay, shared catalog boundaries, simultaneous booking, lifecycle and staged compatibility, midnight/buffer boundaries, effective revisions, stale forms and real rendered assignment errors.

Use only synthetic demo emulators. Optional browser `VITE_AUTH_EMULATOR_PORT`, `VITE_FIRESTORE_EMULATOR_PORT` and `VITE_FUNCTIONS_EMULATOR_PORT` allow isolated local ports; default ports are unchanged and emulator mode still requires a demo project and loopback browser. No toolchain install, deployment, production writes, rollout flag changes, recurrence, scheduler or closure worker is included. Deploy the six catalog callables plus compatible event commands and declared indexes, then verify staging index readiness before rollout. Existing assigned occupancy must remain readable if new writers are disabled; never delete history for rollback. New records are organization/event operational data with the existing audit metadata convention, not new user-owned access or delivery storage; command receipts remain covered by account deletion.
