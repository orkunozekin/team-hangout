# Participant check-in assistance

P2.11 adds foreground/simple check-in using the P2.10 attendance records and coach correction API. Self-linked participants and guardians with live `viewSchedule` and `respond` permission may assert attendance for one active canonical participant on an event roster. A participant login, device or affirmative RSVP is not required for coach attendance. Check-in is an assertion, never identity or presence verification; GPS is spoofable. Missing check-in remains unknown and never creates absence.

## Server contract

`getParticipantCheckIn({eventId, participantId})` returns only that authorized participant's attendance status/source/revision, event/schedule revisions, policy and current closure reason. It does not expose the team roster, other participants, contact information or raw samples. `checkInParticipant({eventId, participantId, eventRevision, scheduleVersion, expectedRevision, method, sample?, requestId})` shares the deterministic attendance row and immutable revision history with manual recording. Methods are `simple` and `location`. The server stamps actor, guardian/self source, method and assistance outcome. An existing current-schedule observation cannot be overwritten by household check-in; corrections go through the coach API with a reason. A new schedule requires a fresh assertion and retains prior attendance history.

Every discovery, write and successful-receipt replay checks current account, household grant, enrollment, canonical event/team organization references and committed publication. Discovery pointers and platform support roles grant no authority. New writes additionally require active hierarchy, the server attendance flag, a scheduled event, an open resource, the current revisions and the server-clock check-in window. Receipts may acknowledge a prior success after the window or lifecycle changes, but never after household/enrollment/publication access is revoked. Concurrent guardians/staff serialize on attendance revision. No offline queue is added.

Pilot defaults are 40 minutes before through 120 minutes after start, a 500 m radius, accuracy no worse than 100 m, and sample age no more than 60 seconds. Server time evaluates the window and sample age; future samples fail closed. The server validates finite/ranged coordinates, positive finite accuracy and the immutable event resource-coordinate snapshot, then computes haversine distance. Poor/stale/invalid samples, missing venue coordinates and out-of-radius attempts provide explicit simple/manual fallback. These checks do not prevent spoofing or prove who holds the device.

`setEventCheckInPolicy({eventId, expectedRevision, policy, requestId})` requires live management authority for every event team. Native staff controls expose minutes before (0–120), minutes after (0–240), radius (50–1000 m) and event location assistance. Policy changes increment event revision, append `checkInPolicyHistory`, and honor the scheduling fence. Organization `features.attendance` enables assertions; independent `features.locationAssistance` and the event policy must both allow location. The client never enables organization flags.

## Privacy and native behavior

Expo SDK 54 `expo-location` 19.0.8 requests only When In Use permission after the explicit location button. The app calls current-position once at high accuracy with a 15-second UI timeout; it adds no background modes, service or permission. Denial, services unavailable and timeout leave simple check-in/manual coach help available. Positioning explicitly disables Android secondary settings dialogs (`mayShowUserSettingsDialog: false`); unmet location settings produce the same simple/manual fallback instead of launching another Activity. Backgrounding or unmounting invalidates in-flight acquisition; returning from the native permission prompt preserves the check-in subtree, including Android temporary permission Activities that report background. Acquisition still checks actual foreground state after permission returns. A permission result received while genuinely backgrounded cancels acquisition and requires household reauthorization on return; unrelated background transitions still clear private state.

Coordinates are transient callable input, never written to attendance/history, AsyncStorage, audit or command receipts. Receipts store only the existing SHA-256 payload fingerprint and result. An uncertain request retains its exact payload/sample and request ID only in component memory for explicit retry; reload/unmount discards it and reconciles from the server. No telemetry or raw sample logging is added. Coach views and audit distinguish guardian/self assertions, simple method and spoofable location assistance. Existing organization retention and account deletion semantics apply to attendance history.

## Validation and rollout

Read the exact SDK 54 location/reference source before implementation because the public versioned URL currently redirects to newer documentation. Native binaries must be rebuilt for the new module and permission text. Emulator security tests cover authorization/revocation/replay, private roster boundaries, concurrent writers, lifecycle and resource closures, schedule revisions, independent flags, bounded policy, sample validation and coordinate non-retention. Rendered/native unit tests cover permission denial, timeout, simple/location methods, uncertainty retry, background cancellation, closure states and labels.

Simulator evidence is development evidence, not real-world GPS accuracy, physical-device permission reliability or production readiness. Physical iOS/Android and real venue field tests remain rollout gates, alongside deployment of all three callables, staging validation, consent/privacy review and separately authorized per-organization flags. This step deploys nothing, touches no production data and enables no live flags. P2.12 remains unstarted.
