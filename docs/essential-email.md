# Essential email and private browser information

Step 14 connects existing invitation/version and published-event/revision outboxes to a backend-only transport. No live configuration or delivery is enabled. No marketing, paid access, reminders, RSVP, read receipts or push are included.

## Delivery contract

`resumeEssentialEmail` leases bounded queued/pending work each minute. Transactions acquire a unique 60-second lease; the final check revalidates accounts, verified event contacts, current household grants/rosters/hierarchy, exact event revision, invitation approver/target/access revision/expiry/hash and contact suppression. Stale/revoked work cancels without transport. Send never runs inside a transaction. Invitations reuse the encrypted original token; retries do not create access grants. Existing pre-Step-14 queued invitations remain eligible, with the outbox ID/hash establishing their version binding.

States are queued/pending/sending/sent/failed/cancelled, with attempt count, next attempt, lease, provider ID and sanitized failure code. `sent` means transport accepted, never read or necessarily inbox-delivered. Known pre-send refusal retries at bounded exponential delays (60 seconds through 8 minutes), up to five attempts. Post-send network/server ambiguity, unknown adapter errors after invocation and expired sending leases terminate as `AMBIGUOUS`; support must reconcile provider acceptance before any resend. Exactly-once external delivery is not promised. Resend uses the same outbox provider key where supported; Resend retains idempotency keys for 24 hours. We never automatically retry ambiguous mail across that boundary. Authorization and external acceptance cannot be one atomic transaction: revocation after the last check cannot recall already accepted mail.

The development sink requires both `FUNCTIONS_EMULATOR=true` and `GCLOUD_PROJECT=demo-team-hangout`. It atomically writes one server-only `developmentMailbox/{outboxId}` per key. This contains synthetic plaintext email, including invitation links, and must never be enabled for live data. No client reads/writes the mailbox/outbox/suppression records. Emulator reset removes test mail. Operational logs and staff summaries contain no mail tokens or addresses from other tenants.

Event mail includes title, authorized team labels, exact localized start/end/timezone, place/address, published revision and a private signed-in browser link. It excludes child names, notes and roster/contact lists. Invitation mail names the organization and selected team, and explicitly says time/place are available in the published schedule after acceptance; an invitation alone confirms no event. All mail has browser, help, preferences and privacy fallbacks. Browser event reads use canonical access, expose no participant names and refresh on focus/visibility with stale-response fencing. Event IDs confer no authority; deleted, staged, revoked and unrelated events fail without disclosure. The browser uses session auth persistence and no-referrer policy.

## Suppression and support

`get/setEssentialEmailPreference` manages only the signed-in account's transactional preference with command replay. Promotional consent remains separate and unimplemented. Suppression does not revoke access. The worker also checks tenant-scoped hashed contact suppression. A bounced/complained contact stays suppressed even if the account opts back in; trusted support must first review the corrected contact. Account deletion clears the preference and fences delivery before cleanup.

`recordDeliveryOutcome` is a service-only integration function. It accepts bounce/complaint only when the provider message ID matches the outbox; duplicate reports are safe. It records a redacted failure and tenant contact suppression. There is deliberately no unauthenticated public callback. Production activation requires a signature-verified provider webhook ingestion integration, authenticated support reconciliation and approved retention; this local adapter/test contract does not claim those external gates complete. Do not accept webhook identity from a browser. Staff delivery reporting is org-admin-only, returns purpose/status/counts/actions without addresses or payloads, loads paginated rows and refuses a report over 1,000 entries rather than presenting incomplete counts.

## Approval-gated production sender contract

The backend Resend REST adapter uses single-recipient plaintext transactional mail, bounded request timeout and `Idempotency-Key: essential/{outboxId}`. It never logs provider responses, credentials or links. Secrets stay backend-only: `ESSENTIAL_EMAIL_API_KEY` and existing `INVITATION_DELIVERY_KEY` (32-byte hex key). No native/browser env receives them.

Delivery also requires the server-owned organization `features.essentialEmail=true` flag, rechecked before sending. Delivery is disabled unless all configuration validates: `ESSENTIAL_EMAIL_ENABLED=true`, `ESSENTIAL_EMAIL_POLICY_APPROVED=true`, `ESSENTIAL_EMAIL_FROM`, `ESSENTIAL_EMAIL_REPLY_TO`, `ESSENTIAL_EMAIL_BROWSER_ORIGIN` (exact HTTPS origin) and `ESSENTIAL_EMAIL_PRIVACY_URL` (HTTPS policy). Missing flags, invalid addresses/URLs or missing provider credentials cannot send mail. The demo origin is loopback only. This document approves no actual provider procurement or sender setup.

Before enabling: owner approval of provider, region/processing, quotas/costs, sender/reply/help owner and minor-contact/opt-out/retention policy; verified domain and SPF/DKIM/DMARC; provisioned secrets; hosted HTTPS app/help/privacy pages and Auth domain; verified callback signature ingestion and bounce/complaint exercises; production single-field indexes for outbox status/document-ID scanning and org reports; provider timeout/acceptance reconciliation rehearsal; tested privacy-safe infrastructure logs, mailbox/outbox retention and deletion policy. An approved retention process must clear terminal payloads/contact data; ambiguous invitation ciphertext is kept for reconciliation until that policy exists. Keep live flags off until these gates are evidenced. No deployment, rollout, production migration, domain change or live email occurred in this step.

Provider references: [send API](https://resend.com/docs/api-reference/emails/send-email) and [idempotency retention](https://resend.com/docs/dashboard/emails/idempotency-keys). Expo [SDK 54 reference](https://docs.expo.dev/versions/v54.0.0/) was read before implementation; native dependencies did not change.
